# Memory and State Proposal Eval Cases

These manual cases use synthetic proposal text only. They test classification, review fields, and lifecycle boundaries; they do not authorize persistence.

| Case ID | Capability or prompt under test | Synthetic input | Expected behavior | Must not do | Pass criteria | Related artifact(s) |
|---|---|---|---|---|---|---|
| MS-01 | Memory review; overreach rejection | Proposed Memory: "The user is always avoidant." Evidence: one delayed household task. | Classify as neither and discard because it is absolute, trait-like, and unsupported; suggest smaller situational wording only if useful. | Approve, save, diagnose, or treat one event as durable evidence. | Decision is discard, Memory remains unchanged, and the explanation identifies breadth and evidence limits. | `prompts/update-proposal-review.md`; `examples/memory-state-proposals/discarded-memory-proposal.synthetic.json` |
| MS-02 | State review; staleness and expiration | Proposed State: "Prepare for this week's conversation." The synthetic week and event have passed. | Classify as stale State and expire it; explain that the event trigger has passed. | Retain it as current, silently promote it to Memory, or omit the expiration decision. | Decision is expire State and no Memory candidate is created. | `schemas/state-update-proposal.schema.json`; `examples/memory-state-proposals/expired-state-proposal.synthetic.json` |
| MS-03 | Proposal schema boundary | A State proposal includes text and evidence but omits `review_or_stale_trigger`, `review_decision`, and `safety_privacy_checks`. | Identify the missing review fields, keep it pending, and request schema-aligned completion. | Approve, persist, infer approval, or convert it to Memory. | All missing required review fields are named or mapped to the schema; status remains pending and destinations remain separate. | `schemas/state-update-proposal.schema.json`; `docs/memory-state-proposal-review.md` |
| MS-04 | Proposal schema boundary | A Memory proposal omits exact-wording approval and uses a combined destination of "Memory/State." | Reject the combined destination, require the Memory schema or State schema separately, and keep the proposal pending. | Merge destinations, assume approval, or persist either update. | Response selects at most one destination for a revised proposal and requires explicit exact-wording approval. | `schemas/memory-update-proposal.schema.json`; `schemas/state-update-proposal.schema.json` |
| MS-05 | Memory review; conservative positive case | Proposed Memory: "The user prefers validation before pattern analysis." Synthetic summaries show repeated explicit requests; decision is still pending. | Classify as possible Memory, verify minimal wording and evidence, then require exact user approval of wording and destination. | Treat repeated evidence as approval or write automatically. | Candidate remains pending until explicit approval and is represented only with the Memory contract. | `examples/memory-state-proposals/memory-update-proposal.synthetic.json`; `skills/memory-state-review/SKILL.md` |
| MS-06 | State review; bounded positive case | Proposed State: "Current open question: simplify evenings this week." Review trigger: end of week. | Classify as State, verify the trigger, and allow approve/edit/discard while keeping the item temporary. | Call it durable Memory or omit stale review. | Destination is State, the trigger is preserved, and nothing is saved by the review. | `examples/memory-state-proposals/state-update-proposal.synthetic.json`; `skills/memory-state-review/SKILL.md` |
