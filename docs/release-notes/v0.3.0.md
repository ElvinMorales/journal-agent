# v0.3.0 Release Notes — Journal Mirror MCP Runtime

## Status

This is the release-readiness document for `v0.3.0`. It is safe to create the tag and GitHub release only after this readiness PR is merged and the final validation checklist passes on updated `main`. This PR does not create a tag or GitHub release.

## Summary

`v0.3.0` turns the repository from a manual Journal Mirror scaffold into an optional local/private MCP runtime prototype. It adds a private-vault initializer, guided-intake artifacts, a minimal local MCP server, a proposal review and exact-approved-wording apply workflow, ChatGPT connector setup guidance, a local static runtime viewer, and expanded tests and evals.

The repository remains the public control plane. Real journal content, generated runtime data, configuration, and outputs remain in a user-controlled private data plane outside the repository.

## What Changed Since v0.2.0

- **Guided intake:** added a plain-language prompt, structured response contract, synthetic example, review walkthrough, and boundary evals. Intake creates separate pending Memory and State proposals; it does not approve or persist them.
- **Private-vault runtime initializer:** added a standard-library initializer for a blank, generic vault at an explicit path outside the repository, with dry-run, idempotency, and path-boundary checks.
- **Local MCP server:** added a narrow local stdio runtime with selected-session reads, allowlisted Memory and State reads, separate pending proposals, review metadata, guarded apply, and metadata-only audit tools.
- **Memory/State proposal review and exact apply:** added destination-specific review, exact-wording confirmation, fixed target allowlists, State lifecycle triggers, append-only application, and repeat-apply refusal.
- **ChatGPT connector setup and first run:** documented the stdio/connectivity boundary, conservative tool permissions, synthetic onboarding prompts, refusal checks, and disconnect steps. No live configuration or connectivity is included.
- **Local runtime viewer:** added a local static HTML generator that keeps Memory and State separate, displays bounded runtime metadata, and hides raw journal content by default.
- **Runtime tests and safety evals:** expanded automated boundary regression and manual synthetic intake, prompt-injection, clinical-scope, connector, and viewer cases.
- **Privacy, security, and release documentation:** consolidated validation commands, public/private release gates, limitations, and the safe product handoff.

## Usable Product Path

1. Clone the repository and read the [README](../../README.md), [privacy rules](../../PRIVACY.md), and [security boundary](../../SECURITY.md).
2. Initialize a new private vault outside the repository with the [private-vault runtime package](../private-vault-runtime-package.md).
3. Use the [guided-intake flow](../guided-intake.md) with synthetic inputs while learning it, then keep any real intake and proposals private.
4. Run the [local MCP server](../mcp-local-server.md) against the private vault.
5. If desired and available, connect ChatGPT through a separately reviewed MCP connectivity path by following the [connector setup](../chatgpt-mcp-connector-setup.md) and [first-run walkthrough](../first-run-chatgpt-walkthrough.md).
6. Start with tool inventory, one selected read, and refusal tests before enabling proposal operations.
7. Create separate pending Memory or State proposals, then review, approve, and apply only character-exact wording to the confirmed destination by following the [proposal workflow](../mcp-proposal-approval-workflow.md).
8. Optionally render the [local runtime viewer](../local-runtime-viewer.md) into a protected private output path.
9. Run the [release checklist](../release-checklist-v0.3.0.md) and [runtime validation checklist](../runtime-validation-checklist.md).

## What v0.3.0 Intentionally Does Not Do

- No hosted service or public dashboard.
- No production authentication, authorization, monitoring, or hardening claim.
- No automatic synchronization.
- No automatic Memory updates or automatic State-to-Memory promotion.
- No whole-vault scan or arbitrary file browser.
- No private data committed to the public repository.
- No committed connector configuration, live endpoint, or tunnel setup.
- No committed screenshots, exports, logs, or generated viewer HTML.
- No clinical diagnosis, treatment planning, medication guidance, or replacement for therapy or licensed care.
- No crisis handling beyond high-level safety routing to immediate safety, trusted human support, and appropriate emergency or crisis resources.

## Privacy and Safety Boundary

The public repository is the reusable control plane: code, prompts, schemas, guardrails, documentation, tests, and synthetic fixtures. The initialized vault is the private data plane: real journal entries, selected context, filled Memory, live State, pending proposals, audit records, configuration, and generated outputs.

Generated runtime outputs must stay private. Viewer output may contain filenames, timestamps, statuses, triggers, and other private metadata even when content is hidden. Tests and evals use synthetic data only. Apply requires reviewed character-exact wording, a destination-specific confirmation, and an allowlisted target. Memory remains durable and explicitly approved; State remains temporary and carries lifecycle triggers. Neither silently becomes the other.

These controls reduce known risks; they do not guarantee confidentiality, production security, clinical safety, or therapeutic effectiveness.

## Validation Summary

The release baseline is 9 JSON schemas and 79 automated tests:

- 9 private-vault initializer tests;
- 19 MCP boundary tests;
- 24 proposal/review/apply tests;
- 14 local viewer tests; and
- 13 integrated runtime safety regression tests.

Full commands and pass criteria are in the [v0.3.0 release checklist](../release-checklist-v0.3.0.md). Schema validation and all five suites must pass; full discovery must report 79 tests; MCP server and viewer `--help` commands must exit successfully without runtime activity; and conflict, private-path, generated-output, credential, connectivity, external-asset, and clinical-detail scans must be manually reviewed with no unsafe additions.

## Upgrade and Migration Notes from v0.2.0

- Existing `v0.2.0` users may keep using the manual prompts, schemas, and review workflow.
- `v0.3.0` adds optional local runtime components; adopting them is not required.
- Never point runtime tools at this public repository.
- Initialize a fresh private vault outside the repository, or review any migration manually before changing private data.
- Do not copy private `v0.2.0` notes into public examples, issues, release text, or pull requests.
- Preserve separate Memory and State destinations and explicit approval during migration.

## Known Limitations

- This is a local prototype with manual setup and packaging friction.
- ChatGPT connector availability and controls depend on account, workspace, and current OpenAI product behavior.
- The user must separately review and secure any connectivity path.
- There is no hosted authentication or permissions layer and no production monitoring.
- There has been no formal security audit or clinical-safety certification.
- Manual evals are qualitative, synthetic checks, not comprehensive proof of production safety, privacy, security, or effectiveness.
