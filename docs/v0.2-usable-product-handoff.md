# v0.2 Usable-Product Handoff

## What This Is

Journal Mirror Agent is a public, file-first scaffold for private-first reflection. The public repository supplies inspectable prompts, capabilities, guardrails, schemas, synthetic examples, and evals; a private Obsidian vault or other user-controlled notes system holds all real writing and runtime artifacts. The current product is a manual workflow, not a live app: the user selects context, invokes a prompt, reviews a tentative reflection, and decides whether any separately proposed Memory or State wording should be copied into private notes.

## Use This If

- You want to reflect on a small, deliberately selected piece of private writing.
- You want a framework-neutral file layout that can be adapted to Obsidian or another private notes system.
- You want Memory and State changes to remain visible, separate, optional, and human-reviewed.
- You want public-safe prompts, schemas, walkthroughs, and evals that can be inspected before private use.

## Do Not Use This If

- You need therapy, diagnosis, medical advice, treatment planning, medication guidance, crisis counseling, or emergency support.
- You expect a live service, MCP server, VPS controller, Obsidian plugin, or automatic vault integration.
- You want automatic retention, automatic Memory or State writes, or broad vault scanning.
- You cannot keep real entries, reflections, proposals, Memory, State, and exports outside the public repository.

When immediate safety may be at issue, stop the ordinary Journal Mirror flow and prioritize trusted human support, local emergency or crisis resources, and the safety guidance in `GUARDRAILS.md`.

## Manual User Journey

```text
write privately
-> select a small context
-> run a Journal Mirror prompt
-> receive tentative reflection
-> optionally create separate Memory and/or State proposals
-> review each proposal's wording and destination
-> manually copy only approved wording into private Memory or State
-> use evals and checklists to keep behavior bounded
```

The workflow grants no vault access. A proposal is not approval, and approval is not an automatic write. Memory is durable context the user explicitly approves for future use. State is temporary context with a review, stale, or expiration trigger. State never becomes Memory silently.

## First 30 Minutes

1. Read `README.md` for scope, safety, and start-here navigation.
2. Read `docs/obsidian-private-runtime-guide.md`; create any suggested folders only in a private notes system, never in this repository.
3. Choose one walkthrough in `examples/journal-mirror-walkthroughs/`.
4. Try `prompts/freeform-entry-mirror.md` or `prompts/journal-mirror-session.md` with invented text only while learning the flow.
5. Compare any optional update with the correct proposal schema and a fixture in `examples/memory-state-proposals/`.
6. Read `docs/memory-state-proposal-review.md`, `PRIVACY.md`, `GUARDRAILS.md`, and `EVALS.md` before using private material.

## Adapting It to Private Notes

- Keep the public repository as the versioned control plane and the private notes system as the data plane.
- Copy only the prompts, blank structures, and guidance you need into the private environment.
- Preserve explicit user selection; do not turn convenience into broad notes access.
- Keep the design framework-neutral: prompts, schemas, and review gates should not depend on one model, notes app, or orchestration framework.
- Keep Memory and State in separate private locations, and keep pending proposals separate from approved destinations.
- Prefer minimal summaries and opaque private references over duplicated source writing.
- Keep real entries, selected excerpts, generated reflections, pending proposals, filled Memory, live State, therapy-prep notes, crisis notes, exports, logs, screenshots, local paths, credentials, and private configuration out of Git.
- If a private artifact informs a public improvement, create a new synthetic example or deliberately redacted abstraction; do not publish the source artifact.

## Maintainer Handoff

Before future pull requests:

- Confirm the change belongs to the public control plane and adds no private runtime artifact.
- Run the relevant synthetic evals and the current release checklist.
- Verify that prompts and capabilities still accept user-selected context without implying vault access.
- Verify that Memory stays durable and separately approved, while State stays temporary and carries a review or stale trigger.
- Treat proposal creation, review, exact-wording approval, and manual application as distinct steps.
- Keep the original 14 taxonomy buckets; `agentic-ai-artifact-taxonomy` remains the conceptual source of truth, while Strategic Mirror is reference-pattern inspiration only.
- Put runtime implementation in a separately scoped, explicitly approved issue. Do not let documentation changes quietly add server code, plugins, vault readers, runtime configuration, controller scripts, or automatic persistence.

## Public-Safety Checklist

- [ ] All examples are blank or clearly synthetic.
- [ ] No real journal content, private reflection, live proposal, Memory, State, export, log, screenshot, local path, credential, or identifying detail is present.
- [ ] The public-repo/control-plane and private-notes/data-plane boundary remains explicit.
- [ ] No file claims vault access, automatic retention, automatic persistence, or a live runtime.
- [ ] Memory and State remain separate; State includes a review, stale, or expiration trigger.
- [ ] Proposals remain optional, pending, destination-specific, and inert until human review.
- [ ] Language remains tentative and non-clinical; no effectiveness claims or numeric risk scores are introduced.
- [ ] Crisis indicators replace ordinary reflection with immediate-safety and human-support guidance.
- [ ] Relative links resolve and the validation commands in `docs/release-checklist-v0.2.0.md` pass.
